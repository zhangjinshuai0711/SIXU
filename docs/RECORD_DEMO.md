# SIXU 真实演示录制指南

> 当前尚无用于 README 的真实操作录屏。下述内容是**录制计划**，不能当成已完成的实验或截图。录制完成并核对记录后，再把素材链接添加到首页。

## 展示目标

用 **45–90 秒**回答三件事：① 用户如何调用思序；② 为什么候选会被拒绝或修订；③ 什么证据来自程序检查，而不只是模型复述。

推荐分成两小段，不需要剪成伪造的连续运行记录。

### 第一段：真正执行算术校验

测试题：`137 × 24 + 89`。应将原始运算的结构提交给服务端检查，不应把模型提前算出的数字当作预设正确常量。

画面至少显示：当前 ChatGPT 模型选择、实际 Sixu 工具调用、返回的 `run_id`，以及最终 `checks_declared`、`checks_executed` 与 `verification_status`。

注意：只有服务端确实执行校验时，才能在解说中写“程序已检查”。

### 第二段：受控纠错演示

题目：`18 × 24 + 75`。**明确说明这是受控回归测试**：故意提交错误候选 C1=497，建立正确对照 C2=507，记录错误并修订 C1，再审查最新版并完成。

视频重点显示：

1. C1 初始版本与错误数值；
2. 错误登记、`REVISE` 与新版本；
3. 审查使用 C1 的最新版本，并比较 C2；
4. 最终 `completed` 或真实阻塞状态，不隐藏失败；
5. 若存在服务端检查，显示真实执行记录；若只是 `model_review_only`，如实标注。

**不要将故意注入的错误称为模型独立发现的错误。** 这一段证明协议/版本管理流程，不单独证明推理准确率提升。

## 推荐镜头顺序

| 顺序 | 画面 | 文字 |
| --- | --- | --- |
| 1 | ChatGPT 中选中 Sixu 应用 | 使用当前聊天模型，不另接付费模型 |
| 2 | 输入任务、生成候选 | 有状态的候选记录 |
| 3 | 展示算术检查或受控错误 | 检查与模型审查的区别 |
| 4 | 修订版本及比较 | 旧证据不能冒充新版本 |
| 5 | 最终结果与状态查询 | 以服务端返回为准 |

## 录制前检查

- 隐藏随机 `mcp_url` 路径、API Key、账号信息、本地绝对路径、私人聊天和编辑链接。
- 录制当次完整操作，不要将不同任务的状态拼接成同一次真实运行。
- 不需人为删掉失败或重复调用。可以加速等待片段，但应保留工具结果与状态。
- 如果出现工具错误或没跑完，应直接展示“未完成”，不要制作虚假成功截图。
- 录屏后检查视频内显示的服务版本、候选版本、验证状态，与后台记录一致。
- 尽量输出 MP4 以供完整演示，另导出较短的 GIF 供 README 预览；GIF 应控制尺寸，避免拖慢首页。

## 录制完成后如何发布

1. 将确认不含敏感信息的视频/动图放在 `docs/media/`，或采用经过核对的稳定托管地址。
2. 在 `README.md` 和 `README.en.md` 的“具体例子”部分，用真正的演示封面/动图替换当前教学示意图。
3. 对视频标明是**受控测试、真实问题演示还是基准实验**，不可混用这三种证据类型。
4. 如仅上传 MP4，可在 README 中添加明确的观看链接和一张静态封面；GitHub README 并不保证内嵌视频播放器。
