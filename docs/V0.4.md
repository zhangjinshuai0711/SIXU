# v0.4 接口与校验

v0.4 保留三个 MCP 工具。所有新能力只适用于 `adaptive_search`；
`linear` 和固定 `case_id` 继续原协议，不接受自适应专用参数。

## 启动与模式

`begin_reasoning` 新增可选的 `depth`、`auto_upgrade`、`requirements`、`checks`。
默认 `depth=medium`、`auto_upgrade=true`。`budget` 逐项覆盖预设且是升级后的硬上限。

| 模式 | max_steps | max_candidates | max_revisions | max_no_progress |
| --- | --- | --- | --- | --- |
| medium | 8 | 3 | 2 | 2 |
| deep | 12 | 4 | 3 | 3 |

深度要求至少两个候选的具体比较，审查对象 `review.candidate_id` 已计入，
`review.compared_candidate_ids` 只需列出另一候选，例如审查 C1 v2、
比较 C2 v1 时填 `["C2"]`。比较证据须针对候选的当前版本；旧版证据失效。
中度在修订后仍有当前版本明确错误，或连续无进展且有错误/受阻问题时升级一次。
升级不清零用量，也不突破显式硬上限。`progress=true` 本身不产生进展；
服务依据候选变化、新证据、定义补充和问题状态变化计数。

## 完整算术示例

启动：

```json
{
  "task": "计算 2+2，并提供 total。",
  "depth": "medium",
  "requirements": [
    {"id": "R1", "quote": "2+2", "method": "internal"}
  ],
  "checks": [
    {"id": "T1", "requirement_id": "R1", "type": "arithmetic",
      "left": {"op":"add","left":2,"right":2},
      "right": {"path": ["total"]}, "relation": "eq"}
  ]
}
```

将工具返回的 `run_id`、最新 `stage_key` 与下列产物传给 `advance_reasoning`：

```json
{
  "kind": "adaptive_step", "action": "EXPAND",
  "summary": "构造答案。", "rationale": "检查算术与原题。",
  "candidate": {
    "id": "C1", "strategy": "相加", "answer": "4", "result": {"total": 4}
  },
  "proposed_action": "FINALIZE"
}
```

服务分配 `version=1`，自动执行检查。即使检查通过，选中版本仍需模型审查；
此时返回 `CHALLENGE`，再提交：

```json
{
  "kind": "adaptive_step", "action": "CHALLENGE",
  "summary": "核对当前候选。", "rationale": "审查与最终选择合并。",
  "review": {
    "candidate_id": "C1", "candidate_version": 1,
    "finding": "原题为 2+2，候选答案与 total 均为 4。"
  },
  "finalize": {"selected_candidate_id": "C1", "selected_candidate_version": 1}
}
```

满足条件则同次完成。也可以不传 `finalize`，请求 `FINALIZE` 后独立提交
`kind=adaptive_final` 与相同 ID、版本。省略 `answer/result`，让服务复制权威候选。
若显式提交不同答案或结构化结果，服务拒绝；修改答案必须走 `REVISE`。

## 定义与版本

- 每项 requirement 含 `id`、原题中的精确 `quote`、`method=model|internal`。
  服务校验摘录确实存在，但不能判断模型是否漏提要求或错误理解语义。
- `internal` 要求必须有引用其 ID 的程序检查。`model` 要求需要当前版本审查中
  `review.requirement_ids` 明确覆盖。程序检查不替代模型对完整原题的核对。
- 首次提交后只允许用 `add_requirements/add_checks` 追加有来源的新 ID；
  已有定义不可删除、覆盖或放宽。改变原题条件须新建任务。
- 服务分配候选版本；修订时提交同 ID 的完整候选。旧证据标记失效，问题重新待核对。
  修订动作本身不关闭模型问题；程序问题只能由重新执行且通过的程序检查关闭。
- `review` 仅用于 `VERIFY/CHALLENGE`，必须匹配当前版本；用 `resolve_issues`
  指定本次实际解决的模型问题 ID。旧字段 `resolve_issue` 保留单项形式。
- 审查和候选构造/修改不能在同一步提交。外部报告仍是 `unverified_report`，
  不能伪造服务执行记录，也不能替代针对性审查。

## 检查格式

路径一律是字段名/数组下标组成的数组，相对于候选 `result`；
禁止原型相关路径。所有检查都含唯一 `id` 和 `requirement_id`。

| type | 配置 | 执行内容 |
| --- | --- | --- |
| arithmetic | `left/right`、`relation=eq|le|ge` | 比较表达式与声明数值或边界 |
| structure | `fields` | 固定字段必填、类型、数值范围、数组唯一性 |
| selection | `path/unit/items/budget/requires/excludes`，可选 `cost_path/value_path` | 预算、依赖、互斥、已知且唯一 ID、声明合计 |
| schedule | `path/unit/tasks/capacity/maintenance`，可选 `makespan_path` | 开始时刻、释放、先后、容量及工期一致性 |

表达式节点仅允许有限数字、`{"path":[...]}` 或
`{"op":"add|subtract|multiply|divide","left":节点,"right":节点}`。
不执行字符串代码。表达式两侧合计最多 64 个节点，深度最多 8；
拒绝除零和非有限结果，浮点容差为 `1e-9 * max(1, |left|, |right|)`。
原题运算应逐项录入表达式，让服务计算；不要先让模型算出答案，
再把该答案当作期望常量，以免只是核对模型自己的两个相同断言。

structure 的 field 含 `path/type`，可选 `required`（默认 true）、
数值 `min/max`、数组 `unique`。类型为 string、number、integer、boolean、array、object。
这不是完整 JSON Schema；不支持的定义明确拒绝。

selection 的 item 为 `{id,cost,value?}`；依赖/互斥是 ID 对数组。
`result` 中 path 对应所选 ID 数组。schedule 的 task 为
`{id,duration,demand?,release?,after?}`；维护窗口为 `{from,to,capacity}`，
path 对应任务 ID 到开始时刻的映射。所有区间为 `[start,end)`，重叠维护取最小容量。
时间、数量、金额采用声明单位的非负安全整数，所有计算合计也须在安全范围内。
检查只判断可行性，不推断全局最优。

最多 64 项要求、32 个程序检查；每组数据/引用表/结果数组最多 64 项，
JSON 结果深度最多 8。缺少 result、非法值或执行异常都不会记为通过。
检查结果含候选版本、方法、`verification=service_executed`、passed、失败路径及原因。

## 查询、结束与兼容

普通推进返回当前完整候选、其他候选摘要、未解决问题、检查摘要、本轮变化、
预算和下一动作，不重复原题和完整历史。`reasoning_status` 默认返回原题、
定义和可恢复工作状态；`detail=full` 增加完整候选、证据及历史。
简短回复中的候选摘要不能替代完整历史查询来检视旧版本。

最终权威输出是 `final.answer/result`。服务汇总选中版本的问题，记录未采用候选及原因。
预算结束仍可综合，但 `verification_status=incomplete` 并保留未通过的门槛；
`stop_reason` 说明原因。无候选且预算耗尽时只报告未完成，不编造答案。
`declared_checks_passed` 仅表示已声明程序检查通过，不保证约束提取或正文语义正确。

新状态格式为 v4。旧自适应状态只读、需新建任务；旧线性状态按原协议继续。
TTL、用户隔离、数据库 revision 与配额保持原行为，无新增表迁移。
`metrics.returned_bytes` 仅统计已接受的 begin/advance 响应，不包含状态查询或失败响应；
服务耗时不代表聊天端到端耗时。
