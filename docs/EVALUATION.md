# 实验记录与能力边界

日期：2026-11-08。本文只保留汇总结果，不公开个人运行 ID、原始聊天记录、
客户端应用 ID、临时连接地址或本地审计日志。

## 已有证据

| 测试 | 观察 | 能支持的结论 |
| --- | --- | --- |
| 四任务两阶段排程 | 资源超限被拒绝后修正；新增约束后继续求解，完成两个阶段 | 自定义 MCP 可以提供错误反馈和下一阶段条件 |
| 六任务排程 `sched-01` | 普通组给出合法但非最优的 15；Harness 组最终得到全局最优的 14 | 这一题单次实验的最终结果改善 |
| Python `python-01` | 普通组在同一回答内先错后更正，最终正确；Harness 组最终也正确 | 这一题最终正确性持平 |

六任务排程与 Python 对照都使用同一套早期阶段策略。
Harness 组采用 `feedback=none`，没有把客观分数返回给测试模型用于修正。

排程组 10 次提交，含一轮子问题修复；服务端首次工具启动到最后提交的窗口约 111 秒。
Python 组 6 次提交，无修复；同类窗口约 55 秒。
这不是完整端到端耗时，没有可靠的普通组耗时，因此不能比较速度。
一次提交也不等于一个独立模型会话。

排程结果由约束检查与搜索确认；最终文字证明仍有需要补足的遗漏。
Python 组走通用任务入口，工具当时只确认结构和流程；
实验结束后在本机实际执行原程序，才确认最终 JSON 完全相同。
实际输出没有反馈给测试模型。Python 标准程序可在本机单独运行：

```bash
python3 benchmarks/python-01.py
```

## v0.1.0 的一致性改动

排程实验暴露了“最终答案采用新方案，但部分中间结果还保留旧结论”的问题。
v0.1.0 包含最终逐项核对：保留、替换或标记未解决；
覆盖每个子问题，保存替换前后的记录。
具体规则见 [使用教程](USAGE.md)。

v0.1.0 的 15 项自动检查和已有公网程序客户端流程已通过。
两个聊天对照结果早于最终一致性检查；不把它们冒充为当前版本的聊天验收。
代码中的自动测试主要验证协议与固定评分器，不是模型能力评测。

## 自适应流程首次真实试用

2026-11-08，用户提交了 v0.2.0 自适应流程的 90 分钟会议设计结果；
本地状态和审计记录确认任务完成，7 个动作、1 个候选、0 次修订。
实际轨迹为 `EXPAND → CHALLENGE → VERIFY × 5 → FINALIZE`，
最后因连续两轮模型报告无进展而进入综合，并非因充分验证成功结束。

最终时间分配合计 90 分钟，保留 10 分钟机动，并为六人各安排三轮发言。
行动清单的负责人、期限与验收标准是设计要求，真实任务落实仍未验证。
本次没有普通回答对照，不能据此判断正确率收益，也未实际验证分支和修订动作。

这次试用暴露了调度问题：未关闭的 testable 问题会始终强制 VERIFY，
覆盖模型多次提出的 REVISE。v0.2.1 仅在问题尚未针对当前候选检查时强制验证，
检查后允许按建议进入修订；新问题和候选变更后的问题仍需新检查。
新增两项回归测试后共 21 项检查通过；修复后的聊天模型表现仍待复测。

同日第二次会议题试用完成，轨迹为 `EXPAND → VERIFY → FINALIZE`，
2 个动作、1 个候选、0 次修订，没有登记待解决的搜索问题；
结束原因为模型提出完成，而非无进展或预算耗尽。
时间分配合计 90 分钟，保留 10 分钟缓冲，每人至少 4 分钟明确发言时间。
这确认了新版本的正常完成路径；因未触发待检查问题及修订，
不能据此判定上一轮阻塞修订的路径已通过真实模型复测。
两轮方案均满足已知静态约束，没有普通回答对照，
动作数减少不等于正确率提升，也不代表已测得实际模型计算成本下降。
分支探索、候选修订及客观正确率收益仍待专门验证。

## 不能据此宣称

这些样本不能证明普遍提高复杂任务成功率，也不能证明达到任何深度推理档位。
缺少更大规模未见任务集、重复试验、随机化和生成量匹配的对照。
目前不能区分结构化分解与额外生成量各自带来的效果。

同模型审查不是独立验证，服务端不能认证宿主的实际模型身份。
不需要额外用户消息和确认是使用者对实验界面的回报，
后端日志无法独立证明这些界面行为。
